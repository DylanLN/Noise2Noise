## 一、P0 必须改（实现前解决）

### 1. Feature struct 与 Detector 需求对不上 —— 接口缺口

第五节定义的 Feature：

```
RMS / Peak / FFT / LowEnergy / MidEnergy / HighEnergy / ZCR / Duration / PeakCount / PeakInterval
```

但第七节各 Detector 引用了 Feature struct 中不存在的量：

| Detector | 引用的量 | Feature 中是否存在 |
|---|---|---|
| ImpactDetector | Attack < 50ms、Decay < 300ms | ❌ 无 |
| ChairDetector | "频谱变化缓慢"（需 Spectral Flux） | ❌ 无 |
| DoorDetector | "宽频 / 瞬态 / 混响"（需谱宽、平坦度、衰减尾长） | ❌ 无 |

**结论**：要么给 Feature struct 补字段，要么改 Detector 规则。现在直接写代码，Impact / Chair / Door 三个 Detector 无从实现。

### 2. 缺 Crest Factor（峰均比）—— 本问题最关键的判别特征

楼板冲击噪声与连续噪声（空调、音乐、说话、电器嗡嗡声）**在频带上高度重叠**，都在低频。区分它们的核心特征不是频段能量占比，而是**峰均比**：

```
CrestFactor = Peak / RMS
```

- 冲击噪声：Peak/RMS 很高（瞬态）
- 连续噪声：接近稳态，比值低

现在 Feature 里单独有 Peak 和 RMS，但没有两者的关系。建议：

- 增加 `CrestFactor = Peak / RMS`（短窗计算）
- 配合 `Spectral Flatness`（频谱平坦度，区分宽带冲击 vs 窄带/音乐）

这一项对降低误报率的收益远大于调灵敏度滑块。

### 3. 归一化逻辑有风险

> "归一化：统一音量（相对本底噪声动态归一化，见 Baseline Calibrator）"

如果对**原始信号**做 AGC，会把本底噪声一起抬起来，从而：
- 摧毁绝对阈值（底噪被放大成"冲击"）
- 摧毁峰均比判别力

**建议**：
- 不做信号级 AGC，各特征自行相对 baseline 归一化即可
- 若必须做增益控制，必须设增益上限，防止噪声地板被放大

### 4. Baseline 动态更新有循环依赖，会"适应到失聪"

> "每隔固定时间（如 10 分钟），用**近期未触发事件**的静默片段持续校正 Baseline"

**问题**：触发与否依赖 Baseline，Baseline 又依赖"未触发片段"。当邻居噪声**缓慢抬升**（空调常开、楼下噪音渐大）时：

```
噪声逐渐抬升 → 被算进"近期声音" → Baseline 上移 → 阈值上移 → 听不见该噪声
```

**建议**：
- 跟踪窗口内**低百分位**（如 RMS 第 10 百分位）作为 baseline，而非"未触发片段"
- Baseline 只允许缓慢上移、快速回降，并设绝对下限
- 定义持续触发期间（无静默片段可采样）的更新停滞策略

### 5. Detector 之间无仲裁，事件语义未定义

**判别重叠**：

| 重叠组 | 说明 |
|---|---|
| Footstep（间隔 200~600ms）vs Jump（400~800ms） | 区间部分重叠 |
| Ball vs Jump | 特征几乎相同（规律峰值 + 一致间隔） |
| Door vs Impact | 均为宽带瞬态 |

同一段声音会命中多个 Detector，但 Event Manager 没有：
- **优先级规则**（同时命中时谁优先）
- **去重规则**（同一物理事件只记一次）

**事件语义未定义**："连续 3 次、4 秒内"的"次"指什么？
- 跑步是一段连续过程（PeakCount≥5），算 1 次还是多次？
- Ball 持续拍球算 1 段还是 N 次？

不定义清楚，confirm_count 无法实现。

### 6. Attack/Decay 的测量帧问题

ImpactDetector 要求 Attack < 50ms、Decay < 300ms。

**问题**：4096 长窗（85ms）会把瞬态彻底抹平，测不出 50ms 级别的 attack。

**建议**：
- 在短窗（1024 = 21ms）或原始采样上做亚帧包络提取
- 明确 envelope 的计算位置与时间分辨率
- 否则 ImpactDetector 的规则形同虚设

## 二、P1 强烈建议改

### 7. 线程与实时模型没定义

sounddevice 回调 20ms 一帧，**Python GIL 下不能在回调里跑 4096 点 FFT**。需要明确：

```
回调线程（PCM → 队列，仅此而已）
    ↓
DSP 线程（消费队列，做滤波 / FFT / 特征）
    ↓
Rule Engine tick（帧节拍是多少 ms）
```

以及短窗 / 长窗的对齐关系。建议在文档新增"线程模型 / 数据流 / 延迟预算"一节。

### 8. 延迟预算缺失

从噪声出现到播放反馈的路径：

```
长窗 85ms + hop 42.7ms + 滞回 N 帧 + Event 确认 + Schedule 裁决 ≈ 数百 ms
```

这个数字应明确写出来——"响应感"依赖它，也决定响应是否及时。

### 9. 与邻居的行为级外环（产品风险，非代码风险）

V2 解决了"自身播放 → 自身检测"的内环，但没解决：

```
播放 → 邻居更大声 → 再播放 → 更大声（自动化互相加码）
```

**建议**：
- 每个时间窗口设**最大响应次数上限**
- "fresh episode" 条件：噪声停止 X 秒后再出现，才允许再次响应
- 补充**音量/增益策略**：反馈音需盖过邻居侧的噪声才有效，这是"以噪治噪"有效性的前提，文档未提

### 10. 传感器与摆放位置是最大性能变量

楼板传声对麦克风位置极其敏感（贴地/贴墙 vs 桌上，效果可差一个量级）。文档未写：
- 用什么麦克风
- 放在哪里

**建议**：
- 明确推荐摆放位置，GUI 内提示
- 将**接触式 / 振动传感器**列入选型评估——对楼板低频冲击，接触拾音比空气麦好一个数量级

### 11. DoorDetector 没有规则

只有"宽频 / 瞬态 / 混响"三个特点词，没有阈值，且与 Impact 几乎同型。

**需要明确**：谱宽、衰减尾长、持续时间等判别量。否则无法实现。

## 四、需要你决策的点

1. **静音窗口"只记录不响应"是否接受为默认** —— 这是隐私/打扰边界的核心决策，建议做成默认而非可选项。
2. **响应强度策略**（最大响应次数、音量上限）是否做成硬限制，防止"以噪治噪"变成"噪音战争"。
3. **是否评估接触式传感器** —— 改动大但效果显著；若不做，需在文档中写明空气麦的预期性能与摆放要求。
