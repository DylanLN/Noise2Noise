3. 蓝牙路径：保留 V4 的全部适配逻辑（采样率降级协商、

4. 两条路径共用同一套 Feature Extractor / Rule Engine / Event Manager /
   Schedule Manager 逻辑，差异只体现在 Audio Capture 层的参数协商

5. 明确：本设计不引入任何需要额外购买的硬件

   用户用手头已有的麦克风（不论有线还是蓝牙）即可运行
```

# 一、项目背景

住宅楼层之间由于楼板结构传播，脚步、跑步、拖动家具、拍球、重物撞击等低频冲击噪声具有较强的传播能力。

传统录音软件只能记录声音，无法自动识别噪声事件。

本项目目标是实现：

> 自动监听
>
> 自动检测
>
> 自动判断
>
> 自动响应

无需任何 AI 模型训练。

无需联网。

无需上传数据。

完全本地运行。

不需要额外购买或扩展硬件，用现有麦克风（有线或蓝牙）即可。

# 二、输入设备自适应（新增，支持两类麦克风）

这一节是本版本的核心，负责把"有线/USB麦克风"和"蓝牙麦克风"这两种完全不同的音频链路，统一抽象成对后续 Feature Extractor / Rule Engine 透明的同一套接口。

## 2.1 设备类型自动识别

```
启动时，系统枚举可用输入设备，通过设备名称/驱动信息判断类型：

  含 "Bluetooth" / "BT" / 已知蓝牙芯片厂商标识 → 判定为蓝牙路径
  其余（USB麦克风、3.5mm耳机麦、笔记本内置麦克风、声卡输入）→ 判定为有线路径

GUI 在设备下拉框中标注类型，例如：
  ▼ [有线] Realtek 内置麦克风
  ▼ [有线] USB Microphone (Blue Yeti)
  ▼ [蓝牙] XXX Headset Microphone

用户也可以在识别有误时手动强制指定类型（极少数USB转蓝牙适配器等边缘情况）
```

## 2.2 有线/USB 路径（默认、推荐，多数用户属于此类）

```
采样率：48000Hz 优先（现代声卡/USB麦克风普遍原生支持），
        打开失败时按 48000→44100→16000 依次回退，
        不需要蓝牙级别的探测协商流程

延迟：典型 <20ms（USB/声卡驱动延迟，远低于蓝牙的100~300ms）

Mute Gate：
  Ignore Window 使用固定小余量（默认 200ms，覆盖房间混响尾音即可）
  不需要"提前暂停"这种蓝牙才需要的时序补偿，
  播放开始时同步暂停采集即可，延迟可忽略

首次启动延迟自测（有线路径也执行一次，安全兜底）：
  目的：捕获少数"USB转蓝牙适配器 / 蓝牙耳机被识别成USB音频设备"的
        误判场景——此类设备链路内藏蓝牙延迟，若仍按200ms余量处理，
        播放尾音会重新进入检测，导致自触发死循环
  做法：启动时播放一次已知短音，测量"发出播放指令→麦克风检测到峰值"
        的时间差，作为实测延迟写入 config
  影响：实测延迟 <50ms → 按有线路径 200ms 固定余量处理；
        实测延迟明显偏高（链路内藏蓝牙）→ Mute Gate 自动切换为
        蓝牙式余量（提前暂停 + 加大 Ignore Window）。
        设备类型自动识别只影响采样率协商与重连逻辑，不影响安全余量

断连处理：
  有线设备理论上不会像蓝牙那样随机断连，
  仅需处理"设备被拔出"这种明确事件（Windows会有设备事件通知），
  提示用户并停止监听，不需要蓝牙式的自动重试重连逻辑
```

这是**推荐路径**：性能最好、延迟最低、不需要额外的延迟自测和余量补偿，逻辑最简单可靠。多数用户直接用电脑自带麦克风或者一根几十元的USB麦克风插上就能达到这个路径的效果，不需要专门购置设备。

## 2.3 蓝牙路径（可选，用户已有蓝牙耳机/音箱时可选用）

延续 V4 的完整适配逻辑，因为背后的协议限制是蓝牙本身固有的，不会因为"也支持有线"而改变：

```
Windows 用蓝牙设备录音会强制切到 HFP/HSP 协议：
  采样率降级：16000Hz（Wideband）优先，8000Hz（Narrowband）兜底
  延迟明显：典型 100~300ms
  双工降质：若输入输出用同一蓝牙设备，播放质量也会被拖累

因此蓝牙路径需要：
  采样率协商（16000→8000降级尝试）
  首次启动延迟自测（播放已知短音，测量往返延迟）
  Mute Gate 提前量 + 加大 Ignore Window
    （= 播放时长 + 实测蓝牙延迟 + 200ms安全余量）
  断连自动重连（间隔递增 1s/5s/15s/30s）
  重连后强制重新标定 Baseline
  建议输出使用有线设备或独立蓝牙音箱，避免双工降质
```

## 2.4 两条路径的公共部分（不因设备类型而变化）

```
Feature Extractor 的短窗/长窗设计（目标时长约21ms/85ms，
  点数按实际协商采样率换算）→ 完全一致，只是有线路径下
  采样率固定48000Hz不需要探测，蓝牙路径下采样率是运行时协商结果

Rule Engine 的所有 Detector 规则（CrestFactor / SpectralFlatness /
  Attack-Decay / Episode语义 / 仲裁去重）→ 完全一致，不区分设备类型

Baseline Calibrator（低百分位跟踪）→ 完全一致，
  只是蓝牙路径在"重连"事件后需要强制重新标定，
  有线路径没有这个触发条件（因为不会无故断连重连）

Schedule Manager（时间窗口/响应次数上限/Fresh Episode冷却）→ 完全一致

GUI 实时频谱/包络显示 → 完全一致，只是状态栏显示的内容不同
  （有线：设备名 + 48kHz；蓝牙：设备名 + 协商采样率 + 实测延迟）
```

## 2.5 参数对照表（供实现参考）

| 项 | 有线/USB路径 | 蓝牙路径 |
|---|---|---|
| 采样率 | 固定 48000Hz | 运行时协商，16000→8000降级 |
| 典型延迟 | <20ms | 100~300ms |
| Mute Gate余量 | 固定200ms | 播放时长+实测延迟+200ms |
| 是否需要延迟自测 | 否 | 是（首次启动执行一次） |
| 断连处理 | 拔出即停止提示 | 自动重连+递增间隔 |
| 重连后是否重新标定Baseline | 不适用 | 是，强制执行 |
| 双工（输入输出同设备）风险 | 无 | 有，建议输出分离 |

# 三、设计目标

软件启动以后：

```
开始监听

↓

识别输入设备类型（有线/USB 或 蓝牙），分别走对应参数分支

↓

（若蓝牙）采样率协商 + 延迟自测；（若有线）直接使用48000Hz

↓

环境本底噪声标定（Baseline Calibration）

↓

检测环境声音（短窗包络 + 长窗频谱，实时显示于 GUI）

↓

判断是否属于目标噪声（含 Crest Factor / Spectral Flux 等判别特征）

↓

滞回状态机确认（IDLE → ARMED → CONFIRMED）

↓

Event Manager 判定 Episode 边界，Detector 仲裁去重

↓

检查是否在允许响应的时间窗口内（Schedule Manager）

↓

检查响应次数上限 / Fresh Episode 冷却（防止与邻居互相加码）

↓

播放反馈声音（Mute Gate 按设备类型使用对应余量暂停采集）

↓

进入冷却 + 对应的 Ignore Window

↓

继续监听
```

### Mute Gate（按设备类型分支，均有延迟自测兜底）

```

  播放开始 → 同步暂停采集
  播放结束 → Ignore Window = 200ms（或首次启动自测得到的实测值）→ 恢复采集

# 六、Feature Extractor

这一层只负责计算，不负责判断，与设备类型无关，仅帧长换算依据实际采样率。

## 双窗口设计

```
短窗（Envelope Window）：目标时长约21ms
  用途：RMS / Peak / CrestFactor / ZCR / 包络跟踪 / Attack-Decay 测量 / 峰值检测

长窗（Spectral Window）：目标时长约85ms，50% overlap
  用途：FFT / Spectral Centroid / Spectral Flux / Spectral Flatness / 频带能量比例
```

频率分辨率约 11.7Hz，与采样率无关（长窗固定时长，随采样率换算点数）。

## Feature struct

```
Feature
{
  // —— 短窗特征 ——
  RMS                   float
  Peak                  float
  CrestFactor           float   // = Peak / RMS，核心判别特征
  ZCR                   float

  Envelope              float[]
  AttackTime            float   // ms
  DecayTime              float   // ms

  // —— 长窗特征 ——
  FFT                   complex[]
  SpectralCentroid      float
  SpectralFlux          float
  SpectralFlatness      float

  LowEnergyRatio        float   // 20~150Hz 能量 / 总有效带宽能量
  MidEnergyRatio        float   // 150~1000Hz
  HighEnergyRatio       float   // 1000Hz ~ 有效上限（随采样率变化）

  // —— 滑动窗口统计量 ——
  Duration              float
  PeakCount             int
  PeakInterval          float[]
  IntervalVariance      float

  // —— 相对 Baseline 归一化后的量 ——
  RMS_norm              float
  LowEnergy_norm         float
}
```

## 特征定义表（实现与验收的唯一依据）

低频下界固定 20Hz（与高通滤波对齐）；总有效带宽 = 低/中/高三个频带的并集。

| 特征 | 定义 |
|---|---|
| RMS | 短窗内均方根，`√(Σ x² / N)` |
| Peak | 短窗内 \|x\| 的最大值 |
| CrestFactor | `Peak / RMS`，短窗内计算 |
| ZCR | 短窗内过零次数 / N |
| Envelope | 对短窗内原始样本以 5ms 为步长取 \|x\| 峰值，再做峰值保持 + 指数衰减平滑（衰减时间常数 ~50ms） |
| AttackTime | 包络从峰值的 10% 升到 90% 所需时间（ms），用上述亚帧包络测量，不依赖长窗 FFT |
| DecayTime | 包络从峰值的 90% 衰到 10% 所需时间（ms） |
| FFT | 长窗加汉宁窗后的复频谱 |
| SpectralCentroid | `Σ(f·\|X\|) / Σ\|X\|`，加权频率中心 |
| SpectralFlux | 相邻长窗归一化幅度谱的 L1 距离：`Σ_k \|X_n[k] − X_{n−1}[k]\|` |
| SpectralFlatness | 频带内幅度谱的几何均值 / 算术均值 |
| LowEnergyRatio | 20~150Hz 能量 / 总有效带宽能量（长窗） |
| MidEnergyRatio | 150~1000Hz 能量 / 总有效带宽能量（长窗） |
| HighEnergyRatio | 1000Hz~有效上限 能量 / 总有效带宽能量（长窗，上限随采样率） |
| Duration | Ring Buffer（默认5秒）内连续超门槛帧所跨的时间长度 |
| PeakCount | Ring Buffer 内超过峰值门槛的峰个数 |
| PeakInterval | 相邻峰值时间戳之差序列 |
| IntervalVariance | PeakInterval 的相对标准差（std / mean），度量节奏一致性 |
| RMS_norm | `RMS / Baseline_RMS` |
| LowEnergy_norm | `LowEnergyRatio / Baseline_LowEnergyRatio` |

## CrestFactor 的噪声地板约束（判定必须避开随机噪声）

CrestFactor 的物理下限不是 0，而是**随机噪声在给定窗长下的预期峰均比**：

```
CrestFloor(N) = √(2·ln N)        // N = 短窗实际采样点数
  16kHz/21ms ≈ 336点 → 约3.4
  48kHz/21ms ≈ 1008点 → 约3.7
```

因此 Detector 中的有效 Crest 判定阈值必须不低于噪声地板，避免安静房间的
本底随机噪声周期性越线被误判为冲击：

```
有效Crest阈值 = max( 配置的 crest_factor_min ,  CrestFloor(N) + 1.0 )
```

配置中的 `crest_factor_min` 是绝对下限，实际判定取它与"噪声地板+1"的较大者。
默认值（Footstep 4 / Jump 5 / Ball 4 / Impact 6）是初始猜测，
最终值必须由离线标定工具按实测样本确定（见第二十节）。

## 蓝牙 8kHz 降级模式的频带限制

8000Hz（HFP Narrowband）模式下，编解码链约滤除 300Hz 以下频段，
20~150Hz 不再可信，`LowEnergyRatio / LowEnergy_norm` 相关规则降权或禁用
（配置中以 `low_band_dependent` 标记，见第十七节）；
`CrestFactor / PeakInterval / Episode` 等时间结构特征不受影响。

# 七、Baseline Calibrator

```
启动时：10~30秒静默采样，生成初始 Baseline Profile

运行时：滑动窗口取低百分位（P10）作为 Baseline_RMS 候选值
  上移限速（如0.5dB/更新周期），回降较快（如3dB/更新周期）
  设绝对上下限，防止漂移到失控范围

持续触发占比过高时暂停上移，避免"适应到失聪"

设备相关触发条件：
  蓝牙路径：断连重连后强制重新标定
  有线路径：无此触发条件（连接稳定，不需要强制重新标定，
    但用户手动更换麦克风型号后建议手动触发一次重新标定）
```

阈值换算（绝对量与归一化量两个视角，二者对应同一物理阈值）：

```
绝对量：Threshold = Baseline_RMS + sensitivity × Baseline_STD
归一化量：Threshold_norm = 1 + sensitivity × (Baseline_STD / Baseline_RMS)
```

Detector 规则中对 `RMS_norm` 的比较必须使用 `Threshold_norm`，
避免绝对量与归一化量混用（见第九节）。UI 显示为"容忍度"。

# 八、线程模型 / 数据流

```
【音频回调线程】（sounddevice 实时回调）
  职责：仅将 PCM 数据 memcpy 到 Ring Queue，不做任何计算

        ↓

【DSP 线程】
  职责：Preprocessor → Feature Extractor → Rule Engine
  节拍：跟随短窗tick（约21ms，随采样率换算的实际点数）

        ↓

【GUI 主线程】
  职责：接收 DSP 线程推送的显示数据，渲染
  节流：频谱刷新约10Hz

【Response 线程 / 定时器】
  职责：Event Manager → Schedule Manager → Response Engine → Audio Player

【设备监控线程】
  有线路径：仅监听设备拔出事件
  蓝牙路径：监听连接状态，触发断连提示与自动重连流程
```

## 延迟预算（两条路径分别列出）

```
有线/USB路径：
  短窗帧时长 ~21ms + 长窗hop ~43ms + 滞回确认(N2=5) ~107ms
  + Event确认窗口(按Episode) + Schedule裁决<10ms + Mute Gate<20ms
  ────────────────────────────────
  典型总延迟：数百毫秒左右，接近"准实时"

蓝牙路径：
  在上述基础上叠加蓝牙采集延迟(100~300ms) + 若输出也走蓝牙则再叠加播放延迟(100~300ms)
  ────────────────────────────────
  典型总延迟：约1~3秒，用户需要有心理预期，
    建议首次启动时按当前识别到的设备类型，弹窗告知预期延迟量级
```

# 九、Rule Engine

```
Detector 接口（有状态，含滞回状态机 IDLE→ARMED→CONFIRMED）

Episode 语义定义：见第十节（边界规则权威定义，本处不再重复）

Detector 仲裁与去重：
  优先级 Impact > Door > Jump > Footstep > Ball > Chair
  同一时刻多个 Detector 命中时，取优先级最高者，其余记为 Suppressed
  300ms（arbitration_window_ms）内重复的同一事件只记一次

各 Detector 规则（与设备类型无关；完整阈值见第十七节配置文件，本处为语义说明）：

FootstepDetector（跑步/快速脚步）：
  RMS_norm > Threshold_norm         // 归一化量纲，见第七节，勿与绝对量混用
  CrestFactor > 有效Crest阈值        // 见第六节噪声地板约束
  LowEnergyRatio > 60%
  PeakCount >= 5（Episode 内）
  PeakInterval 200~600ms

JumpDetector（蹦跳）：
  LowEnergyRatio > 70%
  CrestFactor > 有效Crest阈值
  PeakCount >= 3
  PeakInterval 400~800ms

BallDetector（拍球）：
  IntervalVariance < 20%
  CrestFactor > 有效Crest阈值
  PeakCount >= 4

ChairDetector（拖家具）：
  Duration > 1s
  MidEnergyRatio 持续存在（Duration 期间不跌出阈值）
  SpectralFlux < 阈值（频谱变化缓慢）

ImpactDetector（撞击/掉落）：
  CrestFactor > 有效Crest阈值（默认 6）
  AttackTime < 50ms
  DecayTime < 300ms
  SpectralFlatness 0.3~0.6

DoorDetector（摔门）：
  SpectralFlatness > 0.6
  AttackTime < 30ms
  DecayTime 200~600ms
  （与 Impact 的区分：Door 衰减尾更长、频谱更宽更平坦）

8000Hz 降级模式备注：
  low_band_dependent=true 的 Detector（Jump/Footstep/Chair）在
  蓝牙 8000Hz 模式下降权或禁用（见第六节频带限制），
  保留时间结构类条件（PeakCount / PeakInterval / Episode / CrestFactor）。
```

# 十、Event Manager

```

↓

Detector 仲裁去重（见第九节）

↓

confirm_count 统计（按Episode计数，按Detector类型可配置）

↓

时间窗口 + 冷却

↓

决定是否触发 Trigger 请求
```

## Episode 边界判定（权威定义）

```
Episode = 单个 Detector 状态机处于 CONFIRMED 的一段连续时间。

开启：Detector 从 ARMED → CONFIRMED 的时刻，视为 Episode 开始
延续：状态保持 CONFIRMED 期间，持续刷新"最近峰值时间戳"
关闭：满足以下任一条件即关闭当前 Episode：
  ① 包络回落到 Baseline 以下 且 PeakCount 停止增长，持续 2 秒
  ② 达到 Episode 最长时长上限（默认 30 秒），强制分段，
     每个分段各计 1 个 Episode（防止连续噪声被无限期算成单个 Episode）
关闭后状态回到 IDLE，再次 CONFIRMED 计为下一个 Episode
```

## confirm_count 语义（滑动窗口计数）

```
滑动窗口 window_sec 内累计 Episode 数 ≥ confirm_count，即产生一次 Trigger 请求。

默认值（初始猜测，最终由离线标定工具确定，见第二十节）：
  Impact / Door：confirm_count = 1，window_sec = 1   # 单次瞬态即触发
  Jump / Footstep / Ball：confirm_count = 2，window_sec = 65
    —— 需要 2 个 Episode 才触发，避免偶发单段噪声误报；
       窗口 65s 保证"持续不间断噪声"（靠 30s 强制分段）也能累计到 2 个
  Chair：confirm_count = 1，window_sec = 3           # 时长型，本身要求 Duration>1s
```

设计属性（文档化，不是缺陷）：短促偶发的一次脚步/一次拍球（只有 1 个 Episode）
不会触发，必须观察到重复发生的节奏，符合"确认连续发生"的产品目标。

# 十四、麦克风摆放建议

```
无论有线还是蓝牙麦克风，物理摆放都会显著影响效果：

  尽量贴近地板放置（而非桌面/悬空），
  楼板结构传声在贴近固体表面处信噪比优于房间中央悬空位置

  避免摆放在空调出风口、冰箱、路由器等常见家用噪声源附近，
  减少无关声音进入 Baseline 统计，干扰阈值自适应

  若麦克风带夹子/支架，贴墙固定优于随意摆放在桌上，
  减少因麦克风本身被碰到/移动造成的误报

  安装完成后建议观察实时频谱面板一段时间，
  确认本底噪声曲线稳定、无异常尖峰后再开始正式使用
```

不引入任何需要额外购买的硬件（不考虑接触式/振动传感器），用户现有的有线或蓝牙麦克风均可直接使用。

# 十九、遗留决策项

```
以下两项维持"建议默认"状态，落地时按建议值作为默认配置：

1. 静默窗口"只记录不响应"作为默认开启（可关闭）。

2. 响应次数上限与固定音量作为"可调但有硬性上限"
   （上限不可突破，例如 max_responses_per_window ≤ 20）。

以下两项已在 V5.1 定案，不再作为遗留项：

3. 首次启动延迟提示：无论有线/蓝牙，首次启动均执行一次延迟自测
   （见第二节2.2），自测后弹窗告知预期响应延迟量级
   （有线 <0.5s；蓝牙约1~3秒），避免用户误以为软件反应慢是 bug。

4. 设备类型自动识别提供手动覆盖：高级设置中提供 [auto / 有线 / 蓝牙]
   三选，默认 auto。自动识别结果仅影响采样率协商与重连逻辑，
   不影响 Mute Gate 安全余量（安全余量由延迟自测兜底）。
```

# 二十、离线阈值标定工具（开发辅助，不随软件分发）

## 目的

第九节/第十七节中的所有阈值（CrestFactor、频带比例、SpectralFlatness、
Attack/Decay、PeakInterval、SpectralFlux 等）当前是初始猜测值，没有实测依据。
本工具用于在开发阶段用真实录音把阈值从"猜测"变成"标定值"。

## 输入

```
samples/
  正样本/    # 跑步.wav  拍球.wav  拖家具.wav  撞击.wav  蹦跳.wav  摔门.wav
  负样本/    # 电视.wav  吸尘器.wav  空调.wav  说话.wav  普通敲门.wav
每个样本 5~30 秒，文件名即类别标注；
用目标部署的同一麦克风/同一采样率录制，保证与部署环境一致
```

## 流程

```
1. 录制/收集样本（用部署目标设备录制，采样率路径与部署一致）
2. 跑与运行时完全相同的 Feature Extractor（dsp/feature.py，第六节公式），
   生成每个样本的特征时间序列
3. 对每个 Detector 在候选阈值网格上扫描，计算：
     召回率 = 正样本中被正确确认的占比
     误报率 = 负样本中被误判的占比
4. 绘制每个 Detector 的工作点曲线，选择"误报率可接受下的最高召回率"点，
   输出建议阈值
5. 将标定结果写回 config.yaml（per_detector.rules 等字段）
```

## 输出

```
calibration_report.md    # 每个 Detector 的阈值建议 + 对应召回率/误报率
config.yaml 更新          # per_detector 阈值替换为标定值
```

## 与运行时的关系

标定工具与运行时共用同一套特征代码（dsp/feature.py），
保证标定环境与部署环境特征一致。运行时不做任何学习，仅使用标定结果。
